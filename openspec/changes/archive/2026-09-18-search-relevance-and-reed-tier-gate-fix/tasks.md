  **Findings (2026-09-18):**
  - `jobs.ts`'s `adzuna_jobs_cache` Firestore doc key: `` `${generateCacheKey(titleStr, locationStr, countryCode, categoryStr)}-${typeStr}-${contractStr}-${limit}` `` — **is** jobType/contractType/limit-sensitive. The doc's `data` field stores the full `JobSearchResponse` (`mean`, `count`, `histogram`, `results`, `provider`) plus `expiresAt`/`timestamp`/`categoryTag`/`job_type`/`contract_type`.
  - `salary.ts`'s `adzuna_distribution_cache` Firestore doc key: `generateCacheKey(titleStr, locationStr, countryCode, categoryStr)` **only** — no jobType/contractType/limit suffix. **Confirmed key parity does NOT hold**: the two caches use structurally different keys. `salary.ts`'s existing category-tag-steal logic guesses `` `${cacheKey}-full-time-permanent-10` `` against `jobs.ts`'s key, which only resolves correctly when the request used the default filters.
  - **Deeper bug found**: `salary.ts`'s event handler destructures only `{ title, location, country, category }` from its query — it never reads `jobType`/`contractType` at all, even though the client (`app/composables/useJobs.ts`'s `fetchHistogram`) already sends both as query params. This is broader than design.md's original framing ("passes empty-string jobType/contractType to Reed") — the values are dropped at the route boundary, not merely defaulted.
  - `resultsPerPage` is never sent by either `fetchJobs` or `fetchHistogram` in `useJobs.ts` — `jobs.ts`'s `limit` is therefore always `Number(undefined) || 10 = 10` in current production usage. This makes the `-10` limit suffix of `jobs.ts`'s key deterministic today, so `salary.ts` can reliably reconstruct the full key as `` `${generateCacheKey(...)}-${typeStr}-${contractStr}-10` `` once it reads and normalizes its own `jobType`/`contractType` query params the same way `jobs.ts` does (`String(x || default).toLowerCase()`).
  - TTL parity: both caches use the same `expiresAt`-based mechanism, the same 30-day default, the same per-category override via the `adzuna_category` collection, and the same "stale UK provider" invalidation check — no TTL divergence risk for the reuse mechanism.
